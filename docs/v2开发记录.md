## 3. 改动

以下百分比都是 165 组场景（调参集 a、b、p 共 85 组，检验集 c 40 组，新检验集 d 40 组）的总利润变化。相邻两次运行之间有约 ±0.3% 的波动。

### 3.1 同一 tick 内 `RUN` → `KILL` → `RUN`（+17.5%）

题面的三条规则：

- 4.2：层不在缓存里时，执行 `RUN` 就把它放入机架缓存和机器缓存。
- 4.3：被终止的作业回到待运行状态，可以重新启动，"已拉取的层留在缓存中"。
- 4.3：运行费是 c·p·(r−s)，s 是启动的 tick，r 是释放资源的 tick。

所以在同一个 tick 里先 `RUN`，立刻 `KILL`，再 `RUN`：第一次启动把镜像层放进缓存，运行费为 0；第二次启动时镜像层都在机器缓存里，拉取时间为 0。代价是拉取费照付一次，传输费付两次。

- 实现：`tryPlace` 给每台机器算两个价，"正常启动"和"预热后启动"，取便宜的。
- 165 组里共预热 1,053,362 次，重复付的传输费合计 0.58M（总成本约 500M）。
- 效果：未开工就被判"来不及"而放弃的工作流，占总价值的比例从 25% 降到 21%；完成的工作流从 64.3% 升到 69.2%；164 组变好、1 组变差。

### 3.2 终点的处理和乐观度（+4.3%）

- 诊断：21 个作业以上的工作流占总价值 56%。止损里有一类是作业已完成九成以上的大工作流，共 1272 次、已花 18.6M，其中 1080 次的原因是"预计完成时间超过 T"。例如只剩 1 个作业、价值 20380、剩余成本 764，预计第 519.8 tick 完成而 T=519，整条被放弃。
- 改动：原来是预计完成时间大于 T 收益就记 0。改为对 5 个完工时间情景分别判断，并留容差 `HZ`。`HZ` 取 0 / 2 / 8 / 15 / 30 / 99 时为 +1.5% / +2.0% / +2.9% / +3.3% / +3.7% / +3.1%，取 30。
- 排队延迟的权重 `WK` 从 1 改为 0，再 +0.7%。

### 3.3 机架排序计入仓库拉取费（+0.4%，+0.5%）

- 给候选机架排序时加上"机架缓存里没有、要从仓库拉的层"的拉取费（`RF=1`）：+0.36%。
- 候选机架数 `RK` 从 6 改为 12：+0.50%。
- 这两项都接近噪声水平，只算小幅改进。

### 3.4 CPU 优化（输出不变）

- 候选机架数组改为静态，边生成边按插入方式保留最便宜的 `RK` 个。
- "某镜像在某机架还缺多少"按机架缓存的版本号缓存，不再每次重算。
- `waitFor` 的等待时间超过当前最优方案时提前返回。

## 4. 没采用的尝试

- 开工时扫了 10 组单参数（`DEADK`、`KILLK`、`F0`、`OVK`、`WK`、`MG`、`BB`、`SP`、`THR`），最好的 `OVK=0.6` 只有 +1.1%，说明问题不在参数上。
- 终点的乘性容差 `HM=0.7 / 0.5`：+2.9% / +2.4%，不如加性容差，代码已删。
- 改进 2 之后的联合扫描：`OVK=0.5`、`BB=0`、`MG=0.6`、`KILLK=0.8`、`DEADK=0.4` 持平或更差；`F0=1.3`、`SP=0.3` 各约 +0.3%，在噪声范围内。
- 改进 3 之后又扫 17 组参数，都在 −0.8% 到 +0.4% 之间。
- 预约缓存的时长（`RT0`、`RT1`、`RTK`）和重估周期 `THR`：利润持平，评估次数只少 10% 以内，对 CPU 帮助不大。
- 把候选机架的排序换成 `partial_sort`：`minify.py` 不认识这个名字，压缩版编译失败；后来改成插入式选择，并把名字加进了保留字表。
- 考虑过杀掉长时间不结束的作业重跑：实测已超时的作业还要跑的时间大约是已跑时间的 0.3 倍，重跑不划算，没有做。
