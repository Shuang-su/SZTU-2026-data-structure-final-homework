  - 对话开始时间 19:10:24，源码定稿（`sol.cpp` / `submit.cpp`）时间戳 20:38:05，最后一轮回归结束约 20:40:06，与 89 分 42 秒吻合。
  - 提示：生成本文的会话，运行信息里助手自报的模型名是 Sonnet 5.5，与上面不一致。写课程报告时，请以你确认的实际模型名为准。
- **AI 使用**：题面理解、算法设计、代码、调参、评测脚本、压缩脚本全部由 AI 完成，人只负责提供评测包、选择"从零原创"的路线、提出约束。课程要求如实说明，报告里请照写。
- **没有抄袭**：GitHub 上一份 OJ 得 81 分的公开程序（Misuzu0010 的 StarRing）只用来取题面和当利润基准（编译成 `ref81` 跑同样的场景，只看利润数字）。没有读它的策略，没有改它的代码。该程序的二进制和结果不在本仓库里。
- **OJ 没有提交过**：评测网站要校园认证，AI 进不去，也没有替用户提交（每人只有 10 次机会）。

## 1. 约束与目标

| 约束 | 来源 | 对设计的影响 |
| :--- | :--- | :--- |
| 每组 CPU 1 秒 | 题面 | 最大规模（M=360、T=600、6 万作业）必须在约 0.3 秒内跑完，留足余量 |
| 内存 256 MB | 题面 | 全部状态用定长数组和 vector，无问题 |
| 提交源码严格 < 16384 字节，ASCII、LF | OJ | 开发版 36 KB，要写脚本压缩 |
| 7 类对账全对、零非法指令 | 题面 | 先做对账与合法性，再谈利润 |
| 得分 = 通过组数；每组按利润是否达到阈值 | 题面 | 目标是"利润尽量高"，没有 OJ 阈值，只能以 81 分的基准程序为标尺 |

估计：基准程序约 90% 的阈值水平对应 81 分，所以利润每高 1% 大约多 1 分。这只是推测，没有被 OJ 验证。

## 2. 思路

1. **先把评测环境搭起来，再写策略**。官方只给 Windows 的评测程序，用 CrossOver（wine）运行；写 `run.py` 批量跑场景、读评测报告；写 `dummy.cpp` 空答案程序，先看评测报告的格式。
2. **对账优先**。7 类问题（租户账单、配额余量、机架最短路、机器/机架缓存、告警得分、作业松弛量等）全部增量维护，避免每次查询重算。
3. **把"作业调度"提升为"工作流取舍"**。单个作业好坏不重要，一条工作流整体做不做得完才决定收益。因此每条流估计剩余关键路径、剩余成本，按 5 个完工时间情景算期望收益：划算才开工，开工后不划算就 `KILL` 止损。
4. **时长不公开，只能学**。真实时长与估计的偏差按租户而异，用已完成作业和"已超期仍在跑"的作业学习每个租户的真实/估计比值，向全局比值收缩。
5. **选机分两步**。先按"传输费 + 延迟代价 + 运行费"给机架排序，并向前看一步（后继作业汇集输入的代价）；再在最好的几个机架里逐台机器计价（镜像拉取、等待）。每台机器维护预计释放时间线，允许"预约"一台正忙的好机器。
6. **本地基准**。`gen.py` 按题面范围随机生成场景（a 24 组、b 60 组、练习参数 p1、最大规模 z 6 组），最后再生成 40 组没参与调参的场景 c 作为检验。以基准程序为标尺看利润比。

## 5. 失败与弯路

### 5.1 程序错误

- **数组越界崩溃**：作业数超过 6 万的用例 a05 让 `jobEnd[60000]` 越界，改成 `1<<17`。同类数组 `[4096]` 后来也放大到 `1<<16`。
- **排队延迟估计尖峰**：数据中心整体宕机后，每作业准备时间的指数平均一下冲到 60，所有在跑的流都被算成"不划算"而被 `KILL`。拆成"准备时间"和"排队时间"，并给单次观测封顶后修好，利润比从 0.93 升到 1.04。
- **删失时长估计严重高估**：第一版把所有运行中作业的已耗时都当作时长观测，估计明显偏高；改成只计"已经超期"的作业。
- **压缩脚本两个 bug**：小数 `0.03` 被替换成孤立的 `.`，导致编译失败；标准库名字（`atoll`、`array`）被误当成自己的标识符改名。都改了，并用"四份源码在录制输入上逐字节比对输出"来防回归。
- **环境小坑**：macOS 没有 `<bits/stdc++.h>`（加了垫片头文件）；`timeout` 命令不存在；`tpj` 需要预先建好空的 `ans.txt`；`tune.py` 遇到没有基准的 z 用例会报 `KeyError`。

### 5.2 参数/策略调参失败（85 组或 125 组上的对比）

| 尝试 | 结果 | 结论 |
| :--- | :--- | :--- |
| `KILLK`（止损门槛）0.7 / 1.3 | 比 1.0 差 11–17%（0.975 / 0.918 对 1.10） | 极敏感，保持 1 |
| 按最小松弛量排序（`ORD=1`） | 更差 | 删掉 |
| 按机架容量做准入（`ETA`、`GK`、`bucket`） | 100 与 0.8 结果相同，完全无效 | 删掉整段代码 |
| 把主机架惩罚加进选机（`HK>0`） | 更差 | 删掉 |
| 取消前瞻惩罚（`PEN=0`） | 更差 | 保持 1 |
| 剩余时间随未完成作业数的对数放大，`BB=0.1 / 0.15` | 1.034 / 0.933，大幅下跌 | 只保留很小的 0.03 |
| 完成时间倍数的反馈修正（`MK`） | 125 组 1.1406 对 1.1438，略差 | 没采用，代码已删 |
| 离散度随规模放大（`BS`） | 持平或略差 | 没采用 |
| 周期重估太密（`THR=1 / 2`） | 比 4 / 6 差 | 取 6 |
| `WCAP=30`、`OVK≠1`、`SP≠0.4`、`ADM>0`、`TH0=20` | 均略差 | 保持默认 |

提示：这些对比的噪声约 ±0.3%，小于这个量的差别没有采纳。

### 5.3 想法落空

- **利用告警预测故障**：分析发现告警得分 ≥100 的信号，在 60–95% 的单机故障前出现，中位提前约 30 个 tick。于是做了"近 15 tick 有强信号的机器不放新作业"。结果被中断浪费降了约 4–6%，但总利润反而略低（125 组总利润 266.8M 对 265.4M；单独关闭 `KILL` 时则是 264.2M 对 265.3M，略有提升，但差别在噪声量级），因为避开机器要多付等待和排队代价。最后删掉。
- **按未完成作业数修正完成时间**：数据显示大流（≥25 个作业）完成率只有 12–48%，但预测的利润比实际高一倍以上。几种修正都在噪声内或更差，只留下了 0.03 的小修正。
- **成本表现的难点没解决**：弱势场景（最低约 0.78）多半是小规模、时间窗紧、租户很慢，"已开工但没做完"的浪费占成本 20–30%。

### 5.4 性能

- 最初最大规模 CPU 0.45 秒，a05（超过官方上限的 6 万作业以上）0.59 秒，不合要求。
- 瓶颈依次是：每流每 tick 重估（加脏标记）、最短路用 Dijkstra（改队列式）、链路事件后全部源机架重算（改为只重算受影响的）、时间线里读作业结构体（改为 64 位打包）。
- 最终最大规模 CPU 约 0.33 秒；基准程序同条件下 0.77 秒。
- **CPU 时间保险**的第一版，把时钟按倍数放大来模拟慢机器，降级太激进，利润崩溃；改成按线性预算逐级降级（先停周期重估，再隔 tick 调度，最后只回答对账），模拟慢 5 倍时仍能在 1 秒内结束，但利润掉约四分之一。

### 5.5 最终没解决的问题

- 官方小样例（T=10、T=40，远小于正式范围）利润低于基准（0 对 1408，4336 对 9884），先验参数是按正式规模设的，没有为它们调整。
- 在 40 组检验场景上，约 22% 的场景利润低于基准，最低 0.78。
- 只在 Apple clang（`-std=c++11`）下编译验证，没有 GCC 实测。
- OJ 真实得分未知。
